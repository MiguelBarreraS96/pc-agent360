# Changelog

Todos los cambios notables de este proyecto se documentan en este archivo.

El formato está basado en [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/)
y este proyecto adhiere a [Versionamiento Semántico](https://semver.org/lang/es/).

## [No publicado]

### Agregado
- Se agregó un botón "Consultar Cliente 360" en la vista Home (`frontend/src/app/features/home/`) que navega a la ruta `/consulta360` mediante `routerLink`, con estilo acorde a la identidad visual institucional.
- Se creó el documento de requisitos (formato EARS) para la funcionalidad Consulta Cliente 360, que consulta información consolidada de cliente vía backend intermediario OAuth2 + GraphQL.
- Se creó el documento de diseño técnico (design.md) de Consulta Cliente 360 con patrón BFF, componentes de backend (TokenService, GraphQLClient, circuit breaker, enmascaramiento PII, validación Zod), componentes de frontend (vista lazy consulta360), modelos de datos, manejo de errores, propiedades de correctitud y estrategia de pruebas.
- Se creó el plan de implementación (tasks.md) de Consulta Cliente 360 con tareas incrementales de backend y frontend, pruebas basadas en propiedades para las 6 propiedades de correctitud y grafo de dependencias de tareas.
- Se declararon las variables de entorno de Conecta en `backend/.env.example` (URLs de token y GraphQL, client id/secret, scope, x-user-key y timeouts) con placeholders no reales y defaults documentados en comentarios.
- Se registró `provideHttpClient()` en `frontend/src/app/app.config.ts` para habilitar `HttpClient` en la aplicación Angular.
- Se creó `frontend/src/environments/environment.ts` con el objeto `environment` (`production: false`, `apiBaseUrl: 'http://localhost:3000'`) que apunta al backend propio para las llamadas del frontend.
- Se agregaron las dependencias del backend con versión exacta: `zod` (3.24.1) como dependencia y `jest` (29.7.0), `@types/jest` (29.5.14), `ts-jest` (29.2.5), `supertest` (7.0.0), `@types/supertest` (6.0.2) y `fast-check` (3.23.1) como devDependencies; se añadió el script `test` y se creó `backend/jest.config.js` con preset `ts-jest`.
- Se crearon los tipos externos de Conecta en `backend/src/cliente360/conecta-types.ts` (`TokenRequest`, `TokenResponse`, `ConsultaInput`, `GraphQLRequest`, `GraphQLResponse<T>` y `ConectaClienteData`) con tipado estricto y `readonly` según el diseño.
- Se creó el DTO de respuesta enmascarado en `backend/src/cliente360/cliente360-dto.ts` (`CelularDTO`, `ClienteResponseDTO` como allowlist estricta y el tipo discriminado `ConsultaApiResponse`) que define el contrato único expuesto al frontend con enmascaramiento de PII.
- Se creó `frontend/src/app/features/consulta360/consulta360-models.ts` con los tipos del frontend de Consulta Cliente 360 (`ConsultaRequest`, `ViewState`, `ConsultaResult`, `ConsultaApiResponse`, `ClienteResponseDTO` y `CelularDTO`), espejo del contrato del backend, con interfaces `readonly` y uniones discriminadas.
- Se creó `backend/src/cliente360/cliente360-schema.ts` con el esquema Zod `.strict()` del cuerpo de consulta (`tipoDocumento` literal `CC`, `numeroDocumento` entero positivo ≤ 9.999.999.999) y el helper `validarConsulta` que usa `safeParse` y retorna un resultado discriminado con `code = "VALIDATION_ERROR"` y el `field` inválido o clave no permitida (Req 3.4-3.7).
- Se extendió `backend/src/config.ts` con la interfaz `ConectaConfig` y el bloque `conecta` en `AppConfig`, leyendo credenciales y endpoints de Conecta solo desde variables de entorno con validación fail-fast al arranque (`parseRequiredSecret`, `parseHttpsUrl`, `parseNumberWithDefault`); los secretos faltantes abortan el inicio nombrando la variable sin exponer su valor (Req 9.1, 9.2, 9.3, 9.5).
- Se creó `frontend/src/app/features/consulta360/consulta-cliente.service.ts` (`ConsultaClienteService`, `providedIn: 'root'`) que envía la consulta únicamente al backend propio vía `HttpClient`, aplica timeout de cliente de 15 s y normaliza la respuesta a `ConsultaResult` (éxito/sin datos/error) sin usar `localStorage` ni `sessionStorage` (Req 1.8, 1.9, 2.6, 2.8).
- Se creó `backend/src/cliente360/graphql-client.ts` (`graphqlClient.consultarCliente`) que ejecuta la consulta GraphQL `ConsultaCliente360` contra Conecta con los encabezados requeridos (`Content-Type`, `Authorization: Bearer`, `x-user-key`, `X-Correlation-ID`), envía `numeroDocumento` como valor numérico, aplica timeout de 15 s vía `AbortController`, reintenta una única vez ante 401 invalidando el token y traduce fallas a errores controlados (`UPSTREAM_TIMEOUT`, `UPSTREAM_ERROR`, `CONFIG_MISSING`, `AUTH_UPSTREAM_FAILED`) sin exponer token, secretos ni PII (Req 5.1-5.9, 7.2, 7.3, 8.3).
- Se crearon la plantilla `frontend/src/app/features/consulta360/consulta360.html` y los estilos `consulta360.scss` del componente Consulta360: formulario reactivo (select `CC` y campo de número de documento con mensajes de validación), botón "Enviar" deshabilitado ante formulario inválido o estado de carga, y área de resultados lado a lado con estados idle/loading/noData/error/success renderizados con control flow de Angular 20 (`@switch`/`@if`/`@for`), regiones `aria-live`/`role`, indicador "No disponible" por campo ausente y layout de dos columnas responsivo con verde institucional #00723f (Req 1, 2).
- Se creó el componente `frontend/src/app/features/consulta360/consulta360.ts` (`Consulta360Component`, standalone, `OnPush`) que integra el formulario reactivo (`tipoDocumento` fijo en `CC`, `numeroDocumento` con `Validators.pattern(/^[0-9]{1,15}$/)`), habilita el botón "Enviar" solo con formulario válido y sin consulta en curso, invoca `ConsultaClienteService` convirtiendo el número de documento a `number` y mapea el `ConsultaResult` a los estados de vista `idle`/`loading`/`success`/`noData`/`error` mediante señales (Req 1.1-1.7, 2.1-2.7).
- Se creó `backend/src/cliente360/token-service.ts` (`tokenService`) con caché en memoria del token OAuth2: reutiliza el token vigente mientras el tiempo restante supere el margen de refresco configurado y lo refresca en caso contrario, solicita `client_credentials` vía `POST` con `Content-Type: application/json`, propaga `X-Correlation-ID`, aplica timeout de 5 s con `AbortController`, expone `invalidate()` para el reintento ante 401 y traduce fallas a un error controlado `AuthUpstreamError` (`AUTH_UPSTREAM_FAILED`) conservando la caché vigente, sin registrar token, `client_id` ni `client_secret` (Req 4.1-4.6, 5.8, 7.1, 8.3).
- Se añadió la ruta lazy `consulta360` en `frontend/src/app/app.routes.ts` con `loadComponent` que importa `Consulta360Component`, generando un chunk perezoso independiente para la vista de Consulta Cliente 360 (Req 1.1, 2.1).
- Se creó `backend/src/cliente360/cliente360-service.ts` (`cliente360Service.consultarCliente`) que orquesta la consulta: obtiene el token OAuth2, ejecuta la consulta GraphQL a través de una instancia de circuit breaker a nivel de módulo, enmascara la PII y construye el DTO allowlist retornando `{found:true, cliente}` o `{found:false}` cuando no hay cliente; propaga los errores controlados (`AUTH_UPSTREAM_FAILED`, `UPSTREAM_TIMEOUT`, `UPSTREAM_ERROR`, `CONFIG_MISSING`, `CIRCUIT_OPEN`) y emite logs estructurados (correlationId, ISO-8601, nivel, resultado) sin token, secretos ni PII (Req 3.2, 3.3, 6.4, 6.5, 8.3, 8.4, 8.5, 8.6).
- Se creó `backend/src/cliente360/cliente360-controller.ts` (`consultarClienteHandler`) que valida el cuerpo con `consultaSchema.safeParse` antes de invocar servicios externos y responde `400 { correlationId, error: { code: "VALIDATION_ERROR", message, field } }` ante entradas inválidas; en éxito delega en `cliente360Service.consultarCliente` y responde `200 { found:true, cliente }` o `200 { found:false }`, mapeando los errores controlados a `502`/`503`/`504` con la forma de error genérica `{ correlationId, error: { code, message } }` y delegando errores inesperados al `errorHandler` global sin exponer detalle sensible (Req 3.4-3.9, 2.4).
- Se creó `backend/src/cliente360/cliente360-router.ts` (`cliente360Router`) que define la ruta versionada `POST /seguros/api/v1/cliente360/consulta` enlazada al controller de consulta Cliente 360 (Req 3.1).
- Se montó el `cliente360Router` en `createApp` (`backend/src/app.ts`) después de los middleware de `correlationId` y `express.json()` y antes del `notFoundHandler`/`errorHandler`, y se agregó el método `POST` a la configuración CORS para habilitar el endpoint de consulta Cliente 360 (Req 3.1, 3.2).

### Cambiado
- Se actualizó el script `dev` de `backend/package.json` para cargar el archivo `.env` automáticamente vía `tsx watch --env-file=.env src/server.ts`, permitiendo el arranque local sin variables de entorno externas.
- Se actualizaron los Requisitos 1 y 2 de Consulta Cliente 360 para incorporar un botón "Enviar" explícito que dispara la consulta, la disposición lado a lado del área de resultados junto al formulario, y el mensaje específico "No existe información de este cliente" cuando no hay datos.
- Se crearon los proyectos iniciales de backend Node.js con Express y frontend Angular, junto con sus configuraciones de compilación y documentación de arranque.
- Se agregó el contrato OpenAPI y la colección Postman para el endpoint de disponibilidad del backend.

### Seguridad
- Se evitó la exposición de detalles internos durante un fallo de inicio del frontend.
